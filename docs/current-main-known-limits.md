# 当前主线已知限制

## 1. 目的

明确当前版本“已经做到了什么”和“还没有做什么”，避免把生产候选误当成完全成熟系统。

## 2. 当前已知限制

### 2.1 SQLite 单机口径

当前主线仍以 SQLite 作为运行数据库。

含义：
- 适合单机场景、轻量部署、功能验收
- 不适合把它当成多实例共享数据库方案直接横向扩展

### 2.2 运行治理仍属最小版本

虽然已有：
- 统一配置入口
- 结构化启动日志
- 健康检查
- smoke 验活

但还没有：
- supervisor / systemd / 容器编排说明
- 自动重启策略
- 日志采集与告警闭环
- metrics / tracing

### 2.3 结构化日志只覆盖启动层

当前结构化 JSON 日志主要覆盖启动参数确认。

尚未扩展到：
- 关键 API 请求
- 关键业务动作
- 错误聚合字段

所以它已经能帮助排查“服务怎么起的”，但还不等于完整可观测性。

### 2.4 已有最小自动化 release gate，但还不是完整流水线

现在不仅有 `docs/release-checklist.md`，还已有 `scripts/release_check.py` 作为最小自动化发布检查入口。

当前自动化已覆盖：
- env 文件结构与目标实例 `base_url` 对齐校验
- git working tree clean 校验
- 全量 unittest
- 目标端口监听校验
- `server_starting` 启动日志校验
- smoke 验活

含义：
- 当前版本已经不是“纯人工 checklist”阶段
- 可以支持当前阶段的发布收口与 staging / prod 演练
- 但仍依赖发布人显式触发脚本，不等于 CI/CD 已完成
- 也还没有形成完整的自动部署流水线

### 2.5 配置模板是示例，不是密钥仓库

`deploy/staging.env.example` 与 `deploy/prod.env.example` 只提供参数模板。

不应：
- 存真实密钥
- 直接把示例文件当生产机最终配置

### 2.6 回滚仍是最小回滚

当前回滚口径是：
- 回到上一个已验证 commit
- 重启实例
- 重跑 smoke

这适合当前单机主线，但还不是蓝绿/金丝雀级别的发布回滚体系。

## 3. 当前可接受结论

基于阶段 A/B/C/D 的结果，当前版本可以表述为：

- 可作为“生产候选（production candidate）”
- 具备最小可托管、可验活、可回滚口径
- 但尚未达到“完整平台化生产系统”

## 4. 下一阶段若要继续提升

建议优先级：
1. 把 release checklist 脚本化
2. 增加关键 API / 错误日志的结构化字段
3. 明确常驻托管方式（systemd / supervisor / 容器）
4. 视场景决定是否继续停留在 SQLite
