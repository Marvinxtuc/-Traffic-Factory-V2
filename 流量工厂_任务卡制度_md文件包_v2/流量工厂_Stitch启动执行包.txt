《流量工厂｜Stitch 启动执行包》

一、角色定位
你现在负责“流量工厂”项目的一期产品结构与界面系统设计。
你的职责不是做漂亮稿，而是把“一期最小系统”转成可实现的产品结构、页面骨架、工作台布局和交互流。

二、项目目标
基于流量工厂一期最小闭环，输出一套适合后续工程实现的产品/界面结构方案。

一期主链路固定为：
发现 -> 选题 -> 内容 -> 图片 -> 发布检查 -> 复盘

三、你要解决的问题
1. 让主链路在产品层面清晰可见
2. 让每一个模块有明确入口与上下游关系
3. 让页面结构能支撑 Codex 后续实现
4. 让“发布检查”成为正式工作台，而不是附属弹窗
5. 让系统从 Day 1 就具备“内容工厂”而不是“零散工具页”的感觉

四、设计原则
1. 一期先做工作台，不做花哨营销页
2. 一期先强调流程与结构，不强调视觉炫技
3. 一期所有页面必须服务主链路
4. 页面之间必须能串联，不做孤岛页
5. 发布检查必须有独立页面/工作台
6. 复盘必须有正式入口，不能后补
7. 统一信息架构，避免旧项目那种到处散页
8. 必须考虑未来可扩展，但一期不做大而全

五、你本轮输出的核心内容
你本轮不要直接发散做很多版视觉稿。
必须先输出“一期产品结构定义”，然后再输出“一期页面骨架建议”。

六、信息架构建议
一期建议采用左侧主导航 + 中间主工作区 + 右侧详情/检查/结果面板的工作台形态。

左侧主导航建议只保留：
1. 发现台
2. 选题池
3. 内容工坊
4. 图片工坊
5. 发布检查
6. 复盘台
7. 设置（可后置/简化）

七、一期页面必须覆盖
1. 发现台
功能：
- 来源概览
- 新 signal 列表
- 基础筛选
- 进入选题池动作

2. 选题池
功能：
- topic 列表
- 状态标签
- 优先级
- 平台建议
- 进入内容工坊

3. 内容工坊
功能：
- topic 概览
- content_variant 列表
- 版本切换
- 快速生成/重写动作
- 进入图片工坊

4. 图片工坊
功能：
- 当前内容对应图片资产
- 模板选择
- 生成结果预览
- 进入发布检查

5. 发布检查
功能：
- 检查对象概览
- 检查项分类
- PASS / WARN / BLOCK 汇总
- 问题列表
- 修改建议
- 重新检查
- 允许/阻断发布状态

6. 复盘台
功能：
- 已发布记录
- topic / content / image / check 关联视图
- 基础结果回顾
- 策略备注

八、最关键的产品设计要求
1. 页面必须围绕对象流转，而不是围绕零散按钮
对象流建议始终可追踪：
signal -> topic -> content_variant -> image_asset -> publish_check -> retro_record

2. 每个工作台都要回答：
- 当前对象是什么
- 当前状态是什么
- 下一步动作是什么

3. 发布检查页面必须强化
至少包括：
- 总体结果卡（PASS / WARN / BLOCK）
- 分类结果区
- 问题列表区
- 修改建议区
- 重新检查动作
- 返回上游修改动作

4. 复盘台不做成报表中心
一期复盘台先做“记录与回看中心”

九、一期建议页面输出结构
请按以下结构输出：

# 《流量工厂一期产品结构定义》
## 1. 产品定位
## 2. 一期信息架构
## 3. 主导航设计
## 4. 主链路在产品中的流转方式
## 5. 各模块页面职责
## 6. 关键对象在页面中的呈现方式
## 7. 一期不做什么

# 《流量工厂一期页面骨架建议》
## 1. 发现台页面骨架
## 2. 选题池页面骨架
## 3. 内容工坊页面骨架
## 4. 图片工坊页面骨架
## 5. 发布检查页面骨架
## 6. 复盘台页面骨架
## 7. 全局导航与状态反馈建议

十、页面层统一要求
1. 所有页面应优先服务工程落地
2. 不做复杂动效依赖
3. 布局必须便于后续组件化
4. 不做过多视觉装饰，先把信息结构做好
5. 需要明确列表、详情、操作区、状态区、结果区

十一、给 Codex 的协同考虑
你的输出必须能直接帮助 Codex 做：
1. 页面目录划分
2. 路由划分
3. 页面组件拆分
4. 状态管理范围判断
5. 发布检查模块单独实现

十二、开始时的第一句话
你开始后第一句话必须是：
“我将先输出《流量工厂一期产品结构定义》和《一期页面骨架建议》，先锁定信息架构、主导航、页面职责、对象流转和发布检查工作台，不直接发散视觉稿。”
